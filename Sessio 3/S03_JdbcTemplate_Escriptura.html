Operacions d'escriptura

1. El mètode jdbc.update()

A la sessió anterior vam usar jdbc.query() per llegir dades. Per modificar dades (INSERT, UPDATE, DELETE), Spring ofereix jdbc.update().

Mètode Operació Retorna
jdbc.query(sql, mapper, params) SELECT Llista d'objectes
jdbc.queryForObject(sql, type, params) SELECT (un valor) Un objecte/valor
jdbc.update(sql, params) INSERT / UPDATE / DELETE int = files afectades
Resultat de jdbc.update() El nombre de files afectades et permet saber si l'operació va funcionar:
0 → cap fila tocada (p.ex. DELETE d'un id que no existeix)
1 → una fila inserida/actualitzada/eliminada
N → N files afectades (p.ex. UPDATE massiu)

2. Inserir un producte

2.1 INSERT bàsic

public int save(Product product) {
    String sql = "INSERT INTO products (name, price, description, category, stock) " +
                 "VALUES (?, ?, ?, ?, ?)";

    return jdbc.update(sql,
        product.getName(),
        product.getPrice(),
        product.getDescription(),
        product.getCategory(),
        product.getStock()
    );
}
// Retorna 1 si s'ha inserit correctament

2.2 INSERT recuperant l'ID autogenerat

Sovint necessitem saber l'id assignat per MySQL (auto-increment). El patró és una mica més verbós: 

import org.springframework.jdbc.core.PreparedStatementCreator;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import java.sql.PreparedStatement;
import java.sql.Statement;

public Product saveAndReturnId(Product product) {
    String sql = "INSERT INTO products (name, price, description, category, stock) " +
                 "VALUES (?, ?, ?, ?, ?)";

    KeyHolder keyHolder = new GeneratedKeyHolder();

    jdbc.update(connection -> {
        PreparedStatement ps = connection.prepareStatement(sql,
            Statement.RETURN_GENERATED_KEYS);
        ps.setString(1, product.getName());
        ps.setDouble(2, product.getPrice());
        ps.setString(3, product.getDescription());
        ps.setString(4, product.getCategory());
        ps.setInt(5, product.getStock());
        return ps;
    }, keyHolder);

    product.setId(keyHolder.getKey().longValue());
    return product;
}
💡 KeyHolder El KeyHolder captura la clau primària generada per MySQL. Això ens permet retornar al client l'objecte complet amb el seu id assignat.

3. Actualitzar un producte

public int update(Long id, Product product) {
    String sql = "UPDATE products SET name = ?, price = ?, description = ?, " +
                 "category = ?, stock = ? WHERE id = ?";

    return jdbc.update(sql,
        product.getName(),
        product.getPrice(),
        product.getDescription(),
        product.getCategory(),
        product.getStock(),
        id              // ← L'últim ? és l'id del WHERE
    );
}
// Retorna 1 si existia i s'ha actualitzat, 0 si l'id no existia

El valor retornat és clau per al Controller: si retorna 0, responem 404 Not Found.

Controller amb gestió de 404

@PutMapping("/{id}")
public ResponseEntity<String> update(@PathVariable Long id,
                                      @RequestBody Product product) {
    int rowsAffected = productService.update(id, product);

    if (rowsAffected > 0) {
        return ResponseEntity.ok("Producte actualitzat");       // 200
    }
    return ResponseEntity.notFound().build();                    // 404
}

Transaccions

5. @Transactional: tot o res

🔒

Què és una transacció?

Clica per a la definició

Un conjunt d'operacions que s'executaran totes o cap. Si una falla al mig, les anteriors es desfan automàticament (rollback).

Imagina un sistema bancari: transferir 100€ del compte A al B requereix dues operacions:

  1. Restar 100€ del compte A
  2. Sumar 100€ al compte B

Si la 2a falla però la 1a ja s'ha executat, els 100€ s'han desaparegut. @Transactional impedeix que això passi.

5.1 Exemple: Transferir stock entre productes

@Service
public class ProductService {

    @Autowired
    private ProductRepository productRepository;

    @Transactional  // ← Si qualsevol operació falla, es desfan TOTES
    public void transferStock(Long fromId, Long toId, int units) {
        // Pas 1: Reduir stock del producte origen
        int reduced = productRepository.reduceStock(fromId, units);
        if (reduced == 0) {
            throw new RuntimeException("No s'ha pogut reduir stock");
        }

        // Pas 2: Incrementar stock del producte destí
        int increased = productRepository.increaseStock(toId, units);
        if (increased == 0) {
            // Aquesta excepció provoca ROLLBACK del Pas 1
            throw new RuntimeException("Producte destí no trobat");
        }
    }
}

5.2 Mètodes de repositori per a stock

public int reduceStock(Long id, int units) {
    String sql = "UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?";
    return jdbc.update(sql, units, id, units);
    // La condició stock >= ? evita stocks negatius
}

public int increaseStock(Long id, int units) {
    String sql = "UPDATE products SET stock = stock + ? WHERE id = ?";
    return jdbc.update(sql, units, id);
}
Com funciona per darrere Quan un mètode anotat amb @Transactional s'executa:
1. Spring obre una transacció (BEGIN)
2. Executa tot el mètode
3. Si tot va bé → COMMIT
4. Si hi ha una excepció → ROLLBACK (tot es desfà)

5.3 Regles importants

Regla Per què
@Transactional va al Service, no al Repository El Service és qui decideix l'atomicitat de la lògica de negoci
El rollback només passa amb excepcions no checked (RuntimeException) Spring no fa rollback amb excepcions checked per defecte
El mètode ha de ser public Spring utilitza proxies per interceptar les crides

6. El Controller complet (CRUD)

@RestController
@RequestMapping("/api/products")
public class ProductController {

    @Autowired
    private ProductService productService;

    // ── LECTURA (Sessió 2) ──

    @GetMapping
    public List<Product> getAll() {
        return productService.getAll();
    }

    @GetMapping("/{id}")
    public ResponseEntity<Product> getById(@PathVariable Long id) {
        return productService.getById(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    // ── ESCRIPTURA (Sessió 3) ──

    @PostMapping
    public ResponseEntity<Product> create(@RequestBody Product product) {
        Product saved = productService.create(product);
        return ResponseEntity.status(201).body(saved);          // 201 Created
    }

    @PutMapping("/{id}")
    public ResponseEntity<String> update(@PathVariable Long id,
                                          @RequestBody Product product) {
        int rows = productService.update(id, product);
        if (rows > 0) return ResponseEntity.ok("Producte actualitzat");
        return ResponseEntity.notFound().build();
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        int rows = productService.delete(id);
        if (rows > 0) return ResponseEntity.noContent().build();
        return ResponseEntity.notFound().build();
    }

    // ── TRANSACCIÓ ──

    @PostMapping("/transfer-stock")
    public ResponseEntity<String> transferStock(
            @RequestParam Long from,
            @RequestParam Long to,
            @RequestParam int units) {
        productService.transferStock(from, to, units);
        return ResponseEntity.ok("Stock transferit correctament");
    }
}

7. Resum de JdbcTemplate: fortaleses i límits

Ja tenim un CRUD complet amb JdbcTemplate. Fem balanç:

✅ Fortaleses ❌ Límits
SQL 100% visible i controlat per tu Repetitiu: cada taula requereix el seu RowMapper
Connexions gestionades per Spring Cada camp s'ha de mapejar manualment
Paràmetres segurs amb ? Si canvies un camp a la taula, has de tocar N mètodes
Control total del SQL exacte El codi de INSERT/UPDATE és molt verbós
@Transactional automàtic Escalar a 20 taules = molt de codi repetitiu

📋 Resum de la sessió

  • 1. jdbc.update(sql, params) serveix per a INSERT, UPDATE i DELETE. Retorna el nombre de files afectades.
  • 2. KeyHolder permet recuperar l'ID autogenerat per MySQL després d'un INSERT.
  • 3. @Transactional fa que un mètode sigui atòmic: si una operació falla, totes es desfan.
  • 4. Les transaccions van al @Service, mai al Repository ni al Controller.
  • 5. JdbcTemplate és potent però repetitiu: a la S4 veurem com JPA elimina la repetició.
